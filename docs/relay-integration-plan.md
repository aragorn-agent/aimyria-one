# AIMYRIA GO × 中转站 · 全面绑定方案

> 目标：把「接入中心」从一个**配置页面**升级为**中转站的桌面控制台**。
> 用户不再需要打开网页：登录一次，之后所有密钥、充值、模型、工单、邀请都在托盘程序里完成。
> 原则：功能极其精简，只做用户每天真正会用的动作；每个动作一次点击完成。

---

## 0. 先讲清楚现状（这是方案的地基）

我实测了当前线上接口，不能靠想象做设计：

| 能力 | 端点 | 实测结果 | 能否直接用 |
|---|---|---|---|
| 余额（按 key） | `GET api.aimyria.com/v1/user/balance` | **200**，返回 `remaining=1395.56` | ✅ 已有 |
| 模型列表 | `GET api.aimyria.com/v1/models` | **200**，16 个模型 | ✅ 已有 |
| 用户信息 | `api.aimyria.com/api/user/self` | **404** | ❌ 需服务端开 |
| 密钥列表/创建 | `api.aimyria.com/api/token/*` | **404** | ❌ 需服务端开 |
| 充值 / 兑换码 | — | 不存在 | ❌ 需服务端开 |
| 用量日志 | `api.aimyria.com/api/log/*` | **404** | ❌ 需服务端开 |
| 工单 | — | 不存在 | ❌ 需服务端开 |
| 邀请返利 | — | 不存在 | ❌ 需服务端开 |

**结论**：`go` 目前只能拿到余额和模型。要让桌面端管理中转站，**必须先由服务端（站点侧）开放一组受控接口**。这是本方案的第一阶段，也是不可跳过的前提。

同时注意两件事，它们直接决定架构：

1. **`aimyria.com` 是网关，不是控制台后端。** 控制台（New API 风格）挂在 `aimyria.com` 的站点 vhost 上，`/api/*` 被网关拦截返回 401。所以桌面端不能直接打 `aimyria.com/api/*`。
2. **API Key 和登录会话是两套凭证。** Key 只够查余额和调模型；管理账户必须用**会话令牌**（登录态）。把会话令牌当 API Key 用是错的，反之亦然。方案里两者严格分离。

## 0.1 一条硬要求：会话与 Web 共用，且永不被主动踢下线

产品要求（业主原话）：**桌面端与网页端共用同一个会话；两端都长期保持在线；除了用户自己点「退出登录」，任何页面跳转、窗口关闭、程序重启都不应该结束会话。**

这个要求推翻了「桌面端单独发一套设备令牌」的初版设计。重新设计如下。

### 共用什么、不共用什么

| 东西 | 是否共用 | 说明 |
|---|---|---|
| 账号身份 | **共用** | 同一个 `user_id`，网页和桌面看到的是同一份账户 |
| 登录状态 | **共用** | 网页登录后桌面直接就是登录态；反之亦然 |
| 会话续期 | **共用** | 任一端续期，另一端继续有效（不是「一端续期另一端作废」） |
| Access Token | 各自内存持有 | 短期（15 分钟），不落盘 |
| Refresh Token | 各自一份 | 由同一个会话根签发，**可并存**，互不顶掉 |

关键设计：**Refresh Token 采用「一个会话多个 refresh 凭据」的模型，而不是「单 token 轮换」。**

单 token 轮换（每次刷新作废旧 token）在**多端共用**场景下是错的：桌面端一刷新，浏览器的 token 就失效，用户正在用的网页突然掉线——正是要避免的现象。正确做法是：

- 登录时服务端创建一个 `session`（会话根），并签发 N 个 `refresh credential`，每个绑定一个 `client`（web / desktop）与设备标识；
- 任一端刷新，只轮换**它自己的** refresh 凭据，会话根不变，其它端的凭据继续有效；
- 用户点「退出登录」时，才吊销整个会话根（所有端一起退出）；
- 网页端「已登录设备」列表可以单独踢掉某一台设备。

### 如何做到「永不掉线」

| 场景 | 处理 |
|---|---|
| 关闭窗口 / 最小化到托盘 | **不影响会话**：会话在 Rust 后端，不依赖 WebView 生命周期 |
| 程序重启 / 开机自启 | 启动时从本地加密存储读取 refresh 凭据 → 静默换 access token → 直接是登录态 |
| 页面切换 / 前端重载 | access token 由后端持有，前端通过 IPC 请求，不因 WebView 刷新而丢 |
| 笔记本休眠 / 长时间离线 | 下次联网时静默续期；续期失败仅降级为只读，不弹登录框 |
| Access Token 过期 | 后端自动续期，前端无感（请求拦截器透明重试一次） |
| Refresh 凭据临近过期 | 后台提前 7 天续期 |
| 用户在网页改了密码 | 会话仍有效（密码变更不吊销会话），只有显式「退出所有设备」才吊销 |

**唯一的登出条件**：用户主动点击「退出登录」。

### 服务端会话模型（替代 §2.1 的初版）

```
session
  id, user_id, created_at, last_seen_at, revoked_at(NULL)
  └─ refresh_credential (多条)
       id, session_id, client(web|desktop), device_label, device_id,
       token_hash, expires_at, rotated_at, revoked_at(NULL)
```

```
POST /desktop/v1/auth/login
  { account, password, device:{ id, label } }
  → { sessionId, accessToken, accessTokenExpiresAt,
      refreshToken, refreshTokenExpiresAt, user:{...} }

POST /desktop/v1/auth/refresh
  { refreshToken }
  → { accessToken, accessTokenExpiresAt, refreshToken(新), refreshTokenExpiresAt }
  ※ 只轮换这一条凭据，同一 session 下其它凭据不受影响

POST /desktop/v1/auth/logout            // 吊销整个会话（所有端）
POST /desktop/v1/auth/logout-device     // 只吊销当前设备
GET  /desktop/v1/auth/sessions          // 已登录设备列表（网页端同一接口）
```

### 本地存储（已实现）

`src-tauri/src/relay/session.rs` 已落地：

- **DPAPI 加密**（`CryptProtectData`，绑定当前 Windows 用户）后写入 `~/.aimyria/session.bin`；
- 原子写入（临时文件 + rename），断电不会留下半个文件导致「会话损坏」；
- 版本化信封，未来换存储格式可平滑迁移；
- 登出时**先覆写再删除**；
- 读取失败一律视为「未登录」而非报错——启动路径不能因为一个坏文件崩掉。

### 「长期在线」的安全代价与补偿

永不掉线的反面是「令牌长期有效」，所以补偿措施必须明确：

1. Refresh 凭据**按设备独立**，可在网页端单独吊销；
2. 本地文件是 DPAPI 加密的，换机器无法复用；
3. 提供「退出所有设备」；
4. 敏感操作（改密码、查看密钥明文、支付）仍要求重新验证——会话长不等于权限无限。

> 注意：这不等于「永久不过期」。服务端仍会给 refresh 凭据一个较长的 `expires_at`（建议 180 天，每次使用滑动续期），否则一台丢失的机器就是永久后门。用户感知上仍是「永不掉线」，因为只要他偶尔用一次就会自动续期。

**关键决策：桌面端与 Web 共用同一个会话根，但各自持有一份 refresh 凭据。**

这样既满足「一端登录、两端都在线」，又不会因为桌面端续期而把用户的网页踢下线。桌面端不直接读浏览器的 HttpOnly Cookie——那是浏览器的安全边界，绕过去才是错的；它通过自己的凭据并入**同一个 session**。详见 §0.1。

## 2. 服务端要做的事（必须先做）

新增一组 `/desktop/v1/*` 接口，挂在 `aimyria.com` 上（注意：要绕过网关的 `/api/*` 拦截，用独立前缀）。

### 2.1 认证：与 Web 共用的会话根 + 按设备独立的 refresh 凭据

模型见 §0.1。接口：

```
POST /desktop/v1/auth/login
  { "account": "邮箱或用户名", "password": "…",
    "device": { "id": "<稳定指纹>", "label": "Windows PC" } }
  → 200 { "sessionId": "…",
          "accessToken": "…", "accessTokenExpiresAt": 1730000000,
          "refreshToken": "…", "refreshTokenExpiresAt": 1745000000,
          "user": { … } }
  → 401 { "error": "invalid_credentials" }
  → 429 { "error": "too_many_attempts", "retryAfter": 60 }

POST /desktop/v1/auth/refresh
  { "refreshToken": "…" }
  → 200 { "accessToken": "…", "accessTokenExpiresAt": …,
          "refreshToken": "<新>", "refreshTokenExpiresAt": … }
  ※ 只轮换当前设备的凭据；同一 sessionId 下浏览器的凭据保持有效

POST /desktop/v1/auth/logout           // 吊销整个会话：网页与桌面一起退出
POST /desktop/v1/auth/logout-device    // 只吊销本设备
GET  /desktop/v1/auth/sessions         // 已登录设备列表（网页端复用同一接口）
GET  /desktop/v1/auth/me
```

要求：
- 两种 token 都是**不透明随机串**（32 字节），不是 JWT，服务端可即时吊销；
- Access Token 15 分钟，只在内存；Refresh 凭据 180 天滑动续期；
- **刷新不是全量轮换**：只换当前设备那一条，否则多端共用会互相踢下线；
- 登录失败按 IP + 账号双维度限流（防止撞库）；
- **必须支持二步验证**：账号开了 2FA 时返回 `{ "error": "totp_required", "challenge": "…" }`，桌面端在同一对话框内输入验证码。

> 反例备忘：不要签发「永不过期的令牌」。一旦本机被入侵，等于账户永久沦陷。
> 「用户感觉永不掉线」靠的是**长有效期 + 滑动续期 + 静默刷新**，不是「不过期」。
> 丢失的设备可以通过「已登录设备」踢掉，这是长会话的必要配套。

### 2.2 密钥管理

```
GET  /desktop/v1/keys                     → [{ id, name, keyMasked, createdAt, quota, used, status }]
POST /desktop/v1/keys  { name, group }    → { id, key, name }   // key 明文只返回这一次
POST /desktop/v1/keys/:id/rotate          → { id, key }         // 轮换，旧 key 立即失效
POST /desktop/v1/keys/:id/disable
GET  /desktop/v1/groups                   → [{ id, name, ratio, models }]
```

**设计要点（非常重要）**：
- 列表接口**永远不返回明文 key**，只返回 `sk-...abcd` 掩码。明文只在「创建」和「轮换」的响应里出现一次。
- 桌面端拿到明文后立刻：写进本地密钥库（DPAPI）→ 写进客户端配置 → 落盘完成。**不写日志、不进剪贴板历史、不进崩溃报告。**
- `group`（分组/渠道）决定可用模型和倍率。桌面端默认选「稳定」组，高级用户可改。

### 2.3 充值 / 兑换

```
GET  /desktop/v1/billing/summary          → { balance, todayUsed, monthUsed, planName, autoRenew }
GET  /desktop/v1/billing/packages         → [{ id, name, price, credit, bonus }]
POST /desktop/v1/billing/checkout  { packageId | amount } → { payUrl }   // 打开浏览器完成支付
POST /desktop/v1/billing/redeem    { code } → { credit, balance }
```

**支付不在桌面端内完成**，这是刻意设计：
- 微信/支付宝的支付流程在 WebView 里做既不可靠也难审计；
- 正确做法是桌面端调 `checkout` 拿到一次性 `payUrl`，用系统浏览器打开，支付完成后桌面端轮询 `billing/summary` 刷新余额。

兑换码可以在桌面端直接提交（纯文本，无支付流程）。

### 2.4 用量

```
GET /desktop/v1/usage/summary?range=7d     → { total, byModel: [...], byDay: [...] }
GET /desktop/v1/usage/logs?cursor=…&limit=50 → { items: [...], nextCursor }
```

### 2.5 模型状态

```
GET /desktop/v1/models/status   → [{ model, group, status: "ok"|"degraded"|"down", latencyMs, successRate }]
```

复用现有的 `/v1/models` 做模型清单，这个接口只提供**健康度**。

### 2.6 工单 / 邀请（第二阶段）

```
GET  /desktop/v1/tickets?cursor=…        → 列表
POST /desktop/v1/tickets { subject, body, category } → { id }
GET  /desktop/v1/tickets/:id             → 含回复
POST /desktop/v1/tickets/:id/reply { body }
GET  /desktop/v1/referral                → { code, inviteUrl, invited, earned, pending }
```

## 3. 桌面端架构

### 3.1 后端模块划分（Rust）

```
src-tauri/src/relay/
├─ mod.rs                 统一出口
├─ session.rs             设备会话：登录/续期/登出；令牌存 DPAPI
├─ client.rs              relay HTTP 客户端（复用全局 http_client）
├─ keys.rs                密钥生命周期
├─ billing.rs             充值/兑换
├─ usage.rs               用量
├─ models.rs              模型状态
└─ errors.rs              错误分类（网络/鉴权/额度/服务端）
```

**核心约束（与现有代码一致）**：
- 所有请求走 `proxy::http_client::get()`（已修好的连接池），不新建 Client；
- 主机白名单复用 `RELAY_HOSTS`，防止令牌被发到仿冒域名；
- 会话令牌**绝不进日志**：沿用 `redact_known_secrets`；
- 所有命令返回结构化错误，前端不解析字符串。

### 3.2 密钥落盘链路（一条链路，一个函数）

这是「一键完成接入」的核心，必须做对：

```
createKeyForApp(appId, group?)
  1. POST /desktop/v1/keys            → 拿到明文 key
  2. 存入 secrets 库（DPAPI，按 app 冗余存一份）
  3. 构造该客户端的 provider 配置（复用 live_writer）
  4. 读取现有 live 配置 → 合并 → 原子写入
  5. 回读文件校验（必须看到 key 和 base_url 都在）
  6. 返回结果：{ appId, keyId, maskedKey, writtenPath }
```

失败处理：
- 步骤 1 失败 → 什么本地状态都不改（无副作用）；
- 步骤 4 失败 → 回滚到写入前的备份（live_writer 已有备份机制）；
- 步骤 5 失败 → 标记该 app 为「已写但未验证」，UI 显示黄色而非绿色。

**幂等性**：同一个 app 重复点「接入」，若已有可用 key，默认复用而不是无限创建新 key。需要新 key 时走显式「轮换」。

> 这条很重要：用户多点几次就创建出十几个 key，是这类产品最常见的投诉。

### 3.3 会话存储（已实现）

`src-tauri/src/relay/session.rs`：

- Windows 用 **DPAPI**（`CryptProtectData`，绑定当前用户）加密后存到 `~/.aimyria/session.bin`；
- 不用明文 JSON，不写注册表；
- 原子写入（临时文件 + rename），断电不会留下半个文件；
- 版本化信封，未来换格式可平滑迁移；
- 登出时安全擦除（先覆写再删除）；
- 读取失败一律视为「未登录」，启动路径不会因为坏文件崩溃。

**没有「保持登录」开关。** 按产品要求，会话默认长驻；用户想退出就点「退出登录」。
把长期登录做成默认行为，比做成一个用户要去找的开关更符合「托盘常驻」的产品形态。

### 4.2 接入中心（改造后）

保留现有结构，三处关键改动：

**① 顶部改为「账户条」**（未登录时是登录入口）

```

```

- 支持粘贴；回车提交；
- 失败就地显示原因，不清空已输入内容；
- 2FA 出现时在同一对话框内滑到第二步；
- **不做「记住密码」**——只保存会话凭据（加密）；
- **不做「保持登录」勾选**：长期在线是默认行为，见 §0.1。

登录对话框只在**从未登录**或**用户主动退出后**出现。会话过期不弹框，而是后台静默续期；
续期彻底失败（例如用户在其他设备点了「退出所有设备」）才回到登录态，并说明原因。

### 4.5 为什么切换页面/重载窗口不会掉线

这是「永不掉线」要求的实现要点，值得单独写清楚：

| 层 | 做法 | 为什么 |
|---|---|---|
| Rust 后端 | 会话常驻内存 + 加密落盘 | 进程在，会话就在 |
| 前端 | **不持有 token**，所有请求经 IPC 发往后端 | WebView 刷新、路由切换都不影响会话 |
| 请求层 | 401 → 后端自动 refresh → 重放一次 | 前端代码完全不感知续期 |
| 启动 | 读盘 → 静默 refresh → 已登录 | 无需用户再次输入 |
| 窗口关闭 | 只是隐藏窗口，进程与后端不变 | 托盘常驻的语义 |

## 5. 运行逻辑（关键路径）

### 5.1 首次使用

```
打开 go（托盘常驻，无窗口）
  → 用户点托盘 / 双击图标 → 窗口出现
  → 接入中心显示「登录 Aimyria 账户」
  → 登录成功
  → 自动拉取：账户信息、密钥列表、余额、模型状态
  → 若账户已有密钥：自动匹配到客户端（能匹配上的直接显示已接入）
  → 若没有密钥：提示「点一下自动创建并接入」
```

**自动匹配**：登录后把 `/desktop/v1/keys` 的掩码与本地各客户端配置里的 key 比对，能对上的直接标记「已接入」。这消除了升级用户「怎么全变回接入按钮了」的困惑。

### 5.2 一键接入

```
点「接入」(appId)
  ├─ 有会话？ ── 否 → 弹登录
  ├─ 该 app 已有可用 key 且未过期？ ── 是 → 复用，跳到写配置
  ├─ 创建密钥（POST /keys）
  ├─ 存密钥（DPAPI）
  ├─ 写配置（live_writer，原子写 + 备份）
  ├─ 回读校验
  └─ 更新 UI（绿色 = 已接入且校验通过）
```

整个过程 1–3 秒，进度用行内 spinner，不弹全局 loading。

### 5.3 托盘常驻时的后台行为

| 时机 | 动作 | 开销 |
|---|---|---|
| 启动后 60s | 拉一次概览 + 模型状态 | 一次 |
| 每 15 分钟 | 刷新余额 | 一次 |
| 每 30 分钟 | 刷新模型状态 | 一次 |
| 会话过期前 3 天 | 静默续期 | 一次 |
| 余额低于阈值 | 托盘红点 + 气泡（不弹窗） | 事件驱动 |

**不做**：不做后台轮询用量明细（太贵）、不主动弹窗（托盘程序的底线）。

### 5.4 离线与降级

- 网络不可用：显示上次缓存值 + 「离线」标记，所有写操作禁用并说明原因；
- 会话过期：提示重新登录，**已接入的客户端不受影响**（配置已落盘，key 仍有效）；
- 服务端 5xx：重试 2 次（1s/3s 退避），仍失败则显示「中转站暂时不可用」并给出官网链接。

## 6. 安全底线（不可妥协）

1. **明文只出现一次。** key 明文只在创建/轮换响应里，之后一律掩码。
2. **令牌与 key 分离存储。** 会话令牌 DPAPI 加密；API key 存 secrets 库，按需取用。
3. **日志绝不含密钥。** 复用现有 `redact_known_secrets_strict`，并加一条测试：把假 key 塞进每个错误分支，断言日志里不出现。
4. **主机白名单。** 所有请求复用 `RELAY_HOSTS`；令牌只能发往白名单主机（防止 DNS 劫持把会话令牌送出去）。
5. **可吊销。** 网页端能看到「已登录设备」列表并能踢掉；桌面端登出立即销毁本地令牌。
6. **不自动创建无限密钥。** 一个客户端默认一把；同一 app 重复接入复用现有 key。
7. **退出清理。** 卸载时删除 secrets.bin（与现有 `~/.aimyria` 保留策略需要单独确认——见 §8）。

## 10. 这份方案拒绝了什么（以及为什么）

- **不做完整中转站复制。** 用户管理、渠道管理、公告、日志审计这些是运营后台的活，塞进托盘程序会让它变重。
- **不在桌面端内做支付。** 掉单、对账、退款都会变成桌面端 bug。
- **不共享 Web 会话。** 桌面端需要长期驻留，Web 会话策略不适合，且无法按设备吊销。
- **不做后台常驻轮询用量。** 托盘程序每分钟打一次接口，用户的第一感受是「这软件在偷跑流量」。
- **不自动创建多把 key。** 幂等复用，显式轮换。

## 附录 A：窗口、任务栏与托盘的关系（2026-10-22 修复）

这条问题被报告为「go 没有常驻任务栏」，实际是三个独立缺陷叠加。

### 根因

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | `tauri.conf.json` 写死 `"skipTaskbar": true` | 主窗口**永远**没有任务栏按钮。托盘图标一旦隐藏，进程就在后台无法触达 |
| 2 | `minimizeToTrayOnClose` 为 false 时，关闭窗口直接 `exit(0)` | 点 X 等于退出整个托盘程序，而 X 在其它程序里都是"收起" |
| 3 | `showInTray` 设置项存在但**从未被读取**，UI 也没有开关 | 用户以为能关掉托盘图标，实际毫无作用 |

### 修复

新增 `src-tauri/src/window_policy.rs`，把三个事实一起决定：窗口可见性、任务栏按钮、托盘图标。

| 窗口 | 托盘图标 | 任务栏按钮 | 说明 |
|---|---|---|---|
| 可见 | 显示 | **有** | 最容易被发现的入口 |
| 可见 | 隐藏 | **有** | 托盘没了，只能靠任务栏 |
| 隐藏 | 显示 | 无 | 托盘就是入口，按钮是幽灵 |
| 隐藏 | 隐藏 | **有** | 否则进程彻底失联 |

不变量：**任何状态下至少有一个入口**。有测试遍历全部组合断言这一点。

同时：
- `tauri.conf.json` 改为 `skipTaskbar: false`
- 所有 `show()` 路径（托盘点击、双击图标、深链接、页面加载完成）统一恢复任务栏按钮
- 设置页新增「显示托盘图标」开关，中英文案齐备，保存后立即生效
- 关闭窗口的行为统一走 `close_should_hide()`，尊重用户设置，恢复模式除外

### 验证（真机，Win32 API 枚举）

```
启动（静默）  : visible=False appWindow=True  taskbarButton=False
双击唤起后    : visible=True  appWindow=True  taskbarButton=True   ← 修复点
托盘图标隐藏后: visible=True  appWindow=True  taskbarButton=True   ← 防线生效
设置 minimize=true : WM_CLOSE 后进程存活
设置 minimize=false: WM_CLOSE 后进程退出（尊重用户选择）
```
